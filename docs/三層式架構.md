# 三層式架構   
### 📌目標   
建立統一的專案分層架構與命名規則，提升團隊可讀性、維護性與擴充性。此規範主要適用於後端開發，採用 **三層式架構** (Controller / Service / Repository)。   
 --- 
### 📚 名詞定義   
- **商業邏輯 (Business Logic)**：系統運作核心邏輯，與業務規則密切相關。   
- **業務邏輯 (Application Logic)**：介接使用者與商業邏輯之間的中介，主要為 API 回應 UI。   
- **業務功能（Business Feature / Domain Feature）**：系統中依據實際需求所劃分的功能模組單元，例如使用者管理、訂單處理、報表產出等。作為劃分資料夾、命名 `Profile`、`Service`、`Controller` 等實體的基礎單位。   
- **DtoModel**：內部傳遞資料用，與 Entity 解耦。   
- **Entity**：資料庫映射實體。   
- **ParamModel**：接收前端送入的參數。   
- **ViewModel**：回傳給前端的輸出格式。   
 --- 
   
## 🧱 一、整體架構概述   
專案採用三層式架構，分層如下：
Presentation Layer （表現層 / API Controller）
↓
Service Layer （服務層 / 商業邏輯）
↓
Repository Layer （資料存取層）   
此外，輔助層包含以下目錄：   
- `Helpers`：提供通用工具方法，無商業邏輯性   
- `Models`：定義所有模型（DTO、Entity、Param、ViewModel）

## 🧭 二、各層職責定義   
### 1️⃣ Controller（表現層）   
- 接收 API Request   
- 將 `ParamModel` 轉換為 `DtoModel`   
- 呼叫對應的 Service 方法   
- 將 `DtoModel` 結果轉換為 `ViewModel` 回傳   
   
> 📌 注意：Controller 不實作任何商業邏輯或資料處理，只處理轉換與傳遞。   

 --- 
### 2️⃣ Service（服務層）   
- 實作主要商業邏輯（例如：註冊流程、交易計算）   
- 接收/回傳皆使用 `DtoModel`   
- 可依需求呼叫多個 Repository 或其他 Service   
- 若邏輯無關業務流程，應抽出放至 Helper   
   
> 📌 商業邏輯定義：與業務運作相關、有狀態改變或流程控制的行為   

 --- 
### 3️⃣ Repository（資料存取層）   
- 專責資料 CRUD 操作   
- 與資料庫直接互動，回傳或接收 `Entity`   
- 可使用 Dapper、EF Core 等技術實作   
   
> 📌 使用 Dapper 時也應封裝於 Repository 層中，保持一致性。   

 --- 
### 4️⃣ Helper / Common   
提供共用輔助邏輯，如加解密、格式轉換、Token 處理、參數驗證等，與商業流程無關。   
### 🧩 使用區分：   
|         分類   <br> |                                       說明   <br> |                                            範例   <br> |                     應放資料夾   <br> |
|:------------------|:------------------------------------------------|:-----------------------------------------------------|:---------------------------------|
| **Helper**   <br> |                            處理某項功能的具體工具類別   <br> |          `JwtTokenHelper`、`ImageResizeHelper`   <br> |               `/Helpers/`   <br> |
| **Common**   <br> |                           提供全域共用的靜態定義/結構   <br> |     `RoleEnum`、`GlobalConstants`、`JwtOptions`   <br> |   `/Common/` 或 `/Shared/`   <br> |

### 🚫 禁止行為：   
- 不應有商業流程相關邏輯（如註冊、金流）   
- 不應存取資料庫或呼叫 API   
- 所有函式應為「**純函數**」：相同輸入必有相同輸出，無副作用   
   
### 📌 補充：常用設定與常數區分   
|              類別名稱   <br> |                             本質   <br> |                              常見用途   <br> |                           與 `appsettings.json` 關係   <br> |
|:-------------------------|:--------------------------------------|:-----------------------------------------|:---------------------------------------------------------|
| `GlobalConstants`   <br> |                     編譯期常數（寫死值）   <br> |                       不會變動的旗標、字串等   <br> |                                          通常不來自設定檔   <br> |
|      `JwtOptions`   <br> |                       可組態化設定類別   <br> |                      Issuer、過期時間等   <br> |               來自 `appsettings.json` 並透過 Option 綁定   <br> |

## 🔧 三、介面使用原則（IService / IRepository）   
- 小型專案且無需單元測試 → 可省略介面   
- 中大型或需測試專案 → 應實作介面利於 Mock 測試

## 🔁 五、模型映射設計原則與 Profile 拆分策略   
### ✅ 拆分原則   
1. 以「**業務模組（Domain Feature）**」為主   
2. 每個 Profile 專責單一模組   
3. 每組 Profile 處理單一組明確的轉換邏輯   
   
### 🗂️ 模組切割範例：   
![image](files\image_f.png)    
### 🧩 Profile 範例：UserProfile.cs   
```
public class UserProfile : Profile
{
    public UserProfile()
    {
        CreateMap<CreateUserParamModel, UserDtoModel>();
        CreateMap<UserDtoModel, UserViewModel>();
        CreateMap<UserDtoModel, UserEntity>().ReverseMap();
    }
}

```
🧩 當模組過大時，可進一步細分：   
![image](files\image_k.png)    
📌 建議僅在有大量轉換情境下才拆分，以免過度設計
